# Security model and testing checklist

## Boundaries actually implemented

- All generated code executes only through a fresh **rootless Docker** container (`--network none`, `--read-only`, `--user 65534`, `--cap-drop ALL`, `no-new-privileges`, `--ipc none`, bounded CPU/memory/PIDs and Python process timeout).
- Backend holds Vultr API key; no secrets or host private directories are passed to the sandbox. Script file mount is read-only.
- Docker daemon/sockets remain high-trust and must be protected by Linux account isolation.
- User provides a limited synthetic-data task. Serverless inference proposes code but does **not** grant permissions.
- Deterministic policy reevaluates authorization **before each** of two steps; user can revoke between them. Running step is not preempted by revocation.
- Independent containment scripts genuinely run in Docker; their exit codes, output and timeouts are displayed.
- HMAC audit hashes make edits to existing retained records detectable if the key remains secret. Whole-log truncation, deletion, stolen key, and full host compromise are beyond current protection.
- HTTP Basic under HTTPS is for a hackathon prototype only; it is not multi-user/enterprise-grade authorization.

## Threats not fully solved

- Compromise of the host OS/kernel or rootless daemon; containers are not equivalent to hardened microVMs.
- Container escape exploits; Docker's isolation depends on host security and kernel.
- Abuse of host-side LLM API via stolen demo login. Apply external rate limits/quotas on the Vultr account and web reverse proxy.
- Automatic tracking of secret values through multi-agent workflows; this version avoids putting secrets inside the sandbox instead.
- Perfect prevention of malicious code inside the sandbox. It can still consume allocated resources until timeout.
- External app interception, Cursor/Codex hooks, Windows file protection.

## Comparison to simple sandbox baseline

Experiment A: static permission (initial approval automatically carries to second step). Experiment B: AgentBoundary with stepwise revalidation. Do **not** claim results without measuring. Record unauthorized-step count, benign task completion, overhead, false denies. The example demo is a functional proof-of-mechanism, not new scientific research evidence.

## Data integrity and privacy

- Generated scripts + raw generated code are held in the local SQLite task table; **do not submit real secrets or customer data as prompts**.
- stdout/stderr are returned to the logged-in UI and could contain data generated by the model; no personal data should be included.
- The HMAC key must be protected outside Git. Back up/delete SQLite carefully; log retention policy needed for production.
